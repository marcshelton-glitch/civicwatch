## ADR-002 · Move the loose business documents into the standard structure (resolves D-002)
- **Date:** 2026-09-03
- **Status:** accepted
- **Context:** the `00-` through `70-` retrofit (2026-08-11) added a standard
  category structure, but ~20 pre-existing documents were still sitting at
  the repo root or in ad-hoc folders (`Media campaign/`,
  `Civicwatch Markdown files/`), several as `.docx`/`.html`/`.pdf` exports
  the standard treats as generated artifacts rather than sources. Raised as
  D-002 in `DECISIONS-PENDING.md` on 2026-08-11 with three options.
- **Options considered:**
  - A — commit in-flight work first, then move in one labelled commit
  - B — move on top of uncommitted changes
  - C — leave existing docs where they are, use the new structure only going forward
- **Decision:** **A**, as recommended. By 2026-09-03 the working tree only
  had one unrelated in-flight change (an auto-generated `AGENT-BRIEF.md`
  refresh), which was committed first, so the reorg landed as a single
  reviewable commit (`f28c5d9`).
- **Rationale:** keeps the restructuring commit reviewable and revertible in
  isolation from ordinary work, per the original recommendation.
- **Consequences:**
  - Dated/historical logs and snapshots moved to `00-governance/archive/`.
  - Product mockups/specs (`.docx`/`.html`/`.pdf`) moved to
    `10-product/_exports/`; brand/typography material to
    `30-brand/_exports/`; marketing exports and checklists to
    `40-gtm/_exports/`; the QA tool to `60-ops/_exports/`.
  - `Media campaign/` moved as a unit to `40-gtm/media-campaign/` (a
    cohesive set of social templates + UTM docs, not worth splitting apart).
  - Root tooling/governance anchors that other automation depends on by
    exact path were deliberately left in place: `CivicWatch.md` (updated
    daily by `projects-dashboard` tooling, referenced in
    `.claude/settings.local.json`), `AGENT-BRIEF.md` (auto-generated by
    `build-briefs.sh`), `AGENTS.md`, `CLAUDE.md`, `README.md`,
    `PROJECT.md`, `DECISIONS-PENDING.md`.
  - `CivicWatch Downloaded Files/` was left alone — already gitignored and
    holding local credentials, never part of the tracked repo.
  - Binary/asset-only folders (`brand/`, `civicwatch-brand/`,
    `CivicWatch Media Cards/`, `CivicWatch Social Media Posts/`,
    `Calendar Tasks/`, `FlowChart/`, `marketing/`) were left untouched —
    they're assets, not the "business documents" D-002 scoped, and folding
    them in would have been scope creep on a decision that was specifically
    about documents. Worth a follow-up decision if the same drift concern
    applies to them.
  - A stray LibreOffice lock file (`Media campaign/.~lock.UTM_Link_Builder.xlsx#`)
    could not be deleted from this environment (filesystem only allows
    rename, not unlink) so it was parked in `_to_delete/` instead.

## ADR-003 · Which migration directory is authoritative — `migrations/` or `supabase/migrations/` (resolves D-001)
- **Date:** 2026-09-03
- **Status:** accepted
- **Context:** both `migrations/` (ten numbered SQL files, applied by hand
  via psql/SQL editor) and `supabase/migrations/` (CLI-timestamped files)
  existed with no record of which the live database actually matched.
  Raised as D-001 on 2026-08-11 with three options; recommendation was "C
  first, then B" — diff against live schema before picking.
- **Options considered:**
  - A — `migrations/` canonical, archive the Supabase copy
  - B — `supabase/migrations/` canonical (standard CLI layout)
  - C — diff both against live schema first, then decide with evidence
- **Decision:** **C, then B.** Queried the live project (`hgtofwsvbblumcgbqzat`)
  directly via `supabase_migrations.schema_migrations`, which stores the
  exact SQL executed for every applied migration — not just filenames.
  `supabase/migrations/` is now canonical, rebuilt to exactly match that
  ledger.
- **Rationale:** neither folder was accurate before this. The live ledger
  showed:
  - Four `migrations/` files (001, 002, 009, 010) *were* applied via the
    CLI and are genuinely part of the tracked history.
  - Six `migrations/` files (003–008) built real, still-live tables
    (`user_tracked_reps`, `sent_alerts`, `user_preferences`,
    `opensecrets_net_worth`, `fd_net_worth` OCR columns, `senate_net_worth`,
    `email_sequences`) but were run by hand and never appeared in the CLI
    ledger at all.
  - Five migrations exist live with **no file in either folder**
    (`enable_rls_on_5_unprotected_tables`, `add_performance_indexes`,
    `enable_rls_x_bot_posts`, `add_updated_at_to_push_subscriptions`,
    `drop_erroneous_unique_user_id_index_on_push_subscriptions`) — applied
    straight from the Supabase dashboard and never pulled into the repo.
  - `supabase/migrations/` had two competing `create_push_subscriptions.sql`
    files (bigint id vs. UUID id) with different RLS policy names than what
    was actually live — the committed file had drifted from what was
    actually run.
  - A separate `20260630000003_backfill_bioguide_id.sql` sitting in
    `supabase/migrations/` was a 338KB one-off data backfill (not a schema
    migration) that had never actually been applied.
- **Consequences:**
  - `supabase/migrations/` was regenerated file-by-file from
    `schema_migrations.statements` (ground truth) — 19 files, byte-accurate
    to what's live.
  - The six untracked `migrations/003–008` were copied into
    `supabase/migrations/` under synthetic timestamps matching their
    original apply dates, and registered in the live
    `schema_migrations` table (equivalent to `supabase migration repair
    --status applied`) so `supabase db push` won't try to re-run them.
    `supabase/migrations/` now has 25 files, 1:1 with the 25-entry live
    ledger.
  - `migrations/` is archived in place with a `README.md` pointer (see
    `migrations/README.md`) rather than deleted, for git-blame history.
    Do not add new files there.
  - The stray backfill file was moved to
    `db/backfills/2026-06-30_backfill_fd_net_worth_bioguide_id.sql` and
    **not executed** — 210/503 `fd_net_worth` rows still have a null
    `bioguide_id`; running it is a separate decision from D-001.
  - New, out-of-scope finding surfaced but not resolved here: `tracked_reps`,
    `alerts` (bare), `poll_votes`, `legiscan_cache`, and `users` exist live
    with no creation SQL anywhere in the repo. Origin unknown — needs Marc
    or deploy-history knowledge, not guessing.
